# Backend decisions

Short records of the choices made in Phase 2. Add one when a later phase makes or reverses a
foundational choice.

## D1. Migration-first, not declarative schemas

- **Decision:** `supabase/migrations/*.sql`, written by hand, is the only source of truth. No
  `supabase/schemas/` folder.
- **Reason:** generating migrations from declarative schemas needs `supabase db diff`, which needs
  a shadow database in Docker, and the main development PC cannot run Docker. Keeping both
  representations by hand would create the hybrid the project must avoid. The diff tools also
  miss data changes and some objects (policy renames, some view properties), so their output
  needs hand review anyway.
- **Alternatives:** declarative schemas (`supabase/schemas/` + `db diff`), recommended by Supabase
  for new projects; dashboard edits pulled with `db pull` (rejected: the dashboard is not a
  source of truth).
- **Consequence:** to read the current schema, read the migrations or the generated types.
  Revisit if every developer machine gets Docker; switching later means writing the schema files
  once from the migrations and adopting `db diff` from then on.

## D2. A `private` schema for internals

- **Decision:** trigger functions and future RLS helpers live in `private`, which the Data API
  does not expose and on which the API roles have no rights.
- **Reason:** Supabase grants the API roles everything on new objects in `public`; a helper placed
  there becomes an HTTP endpoint (RPC) by accident.
- **Alternatives:** keep everything in `public` and revoke function by function (easy to forget);
  several domain schemas (more structure than the project needs).
- **Consequence:** a policy that calls a helper needs an explicit `grant usage`/`grant execute`
  in its migration, with a test; the foundation test currently asserts no API role can use
  `private`, and will be updated deliberately when that happens.

## D3. One shared `updated_at` trigger

- **Decision:** `private.set_updated_at()` stamps `updated_at = now()` before every update; tables
  attach it, they do not copy it.
- **Reason:** one tested behaviour; clients cannot forge the value.
- **Alternatives:** per-table triggers (drift), application-side timestamps (forgeable).
- **Consequence:** every row changed in one transaction gets the same stamp.

## D4. Hosted dev project instead of a local-only setup

- **Decision:** `verypinkclub-dev` (free plan, Paris) is the development/staging environment;
  the official local stack runs in CI.
- **Reason:** no Docker on the main PC; a real Supabase project tests migrations, policies and
  types on the same Postgres version and roles as production.
- **Alternatives:** local-only (impossible on this PC); a plain Postgres install (not Supabase:
  no roles, Auth, Storage or API).
- **Consequence:** free-plan limits apply (pauses when idle, no backups, no branching); it only
  ever holds fake data.

## D5. Publishable and secret keys, Supabase's names

- **Decision:** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`,
  `SUPABASE_SECRET_KEY`, matching Supabase's current Next.js guide.
- **Reason:** the new keys rotate independently and the secret key is refused from browsers;
  the legacy `anon`/`service_role` JWT keys are on their way out.
- **Alternatives:** legacy `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY`.
- **Consequence:** the legacy keys can be disabled on every project.

## D6. Configuration checked lazily, plus a check command

- **Decision:** the Supabase settings are validated when a client is created, and on demand by
  `npm run db:check`, not at application start.
- **Reason:** the Phase 1 pages still read mock data and must build and run with no Supabase
  settings at all.
- **Alternatives:** validating at startup (would break every machine without `.env.local`); a
  configuration library (more than two variables need).
- **Consequence:** when the first page depends on the database, move the check to startup
  (`instrumentation.ts`) so a misconfigured deployment fails immediately.

## D7. Three clients in one folder, the privileged one fenced

- **Decision:** `src/lib/supabase/{client,server,admin,env}.ts`; ESLint forbids creating clients
  anywhere else and forbids importing `admin.ts` without an explained exception.
- **Reason:** one place to audit; the secret key cannot leak into a page by habit.
- **Alternatives:** no admin client until needed (then it gets written in a hurry); one generic
  client factory (hides which key is used).
- **Consequence:** the admin client has no caller and an empty allowlist in
  security-foundations.md.

## D8. Generated database types, separate domain types

- **Decision:** `src/types/database.types.ts` is generated by the CLI; components keep using the
  hand-written domain types of `src/lib/types.ts`; loaders map between them.
- **Reason:** the database can change shape without touching components; no hand-written copy of
  the schema to drift.
- **Consequence:** CI fails when the committed generated file does not match the migrations.

## D9. UUID v4 keys with `gen_random_uuid()`

- **Decision:** domain tables use `uuid primary key default gen_random_uuid()`.
- **Reason:** built into Postgres 17, no extension, no guessable ids.
- **Alternatives:** UUID v7 (time-ordered, better index locality) is built in from Postgres 18;
  revisit when the projects move to it.

## D10. No ORM or extra infrastructure

- **Decision:** supabase-js and SQL migrations only; no Prisma, Drizzle, GraphQL layer, queue,
  cache or second database.
- **Reason:** RLS is the security model and it lives in SQL; an ORM connecting with a privileged
  role would sidestep it.
- **Consequence:** complex reads go through views (`security_invoker`) or SQL functions.

## D11. CI checks, never deploys

- **Decision:** `.github/workflows/ci.yml` runs the app checks and, in a second job, rebuilds the
  database from scratch with the Supabase CLI, runs the pgTAP tests and the lint, and compares
  the generated types. It holds no secret and deploys nothing.
- **Reason:** proves on every push that the repository alone recreates the backend, including
  on machines without Docker.
- **Consequence:** deployment to dev/staging and production stays a deliberate `db push`.

## D12. School e-mail + 6-digit code, no password, SSO ready but off

- **Decision:** students sign in with their school address and a code sent by e-mail (Supabase
  email OTP). Institutional sign-in (Microsoft Entra ID or Google Workspace) is implemented behind
  `AUTH_SSO_PROVIDER` and stays off.
- **Reason:** no institutional OAuth credentials exist yet, and inventing them is not an option.
  A code works on any device (a link opened on another phone would not), and no new password to
  forget or leak.
- **Alternatives:** magic link (breaks across devices, prefetched by some mail scanners); password
  (one more secret, plus reset flows); social logins (not a school identity).
- **Consequence:** production needs its own SMTP sender before launch; switching SSO on is a
  configuration step, not a rewrite.

## D13. Signup eligibility in the database, enforced by Supabase Auth, default deny

- **Decision:** a before-user-created hook (`private.before_user_created`) checks every new
  identity against `private.allowed_signup_domains` and `private.signup_email_exceptions`. An
  e-mail-change trigger keeps existing accounts on eligible addresses.
- **Reason:** a frontend check is not a security boundary; the hook covers every signup method,
  including OAuth. With no configuration nothing is allowed, so an unknown production domain can
  never mean "anyone can sign up".
- **Alternatives:** Supabase's "allowed email domains" style settings (not available as such for
  email OTP), an Edge Function hook (more moving parts), checks in Server Actions only (bypassable).
- **Consequence:** each environment configures its domains as data; the real school domain must
  be confirmed before launch.

## D14. Private profiles, no e-mail copy, no role

- **Decision:** `public.profiles` holds only what the site shows about a person; the owner alone
  reads and edits it; the e-mail stays in `auth.users`.
- **Reason:** one source of truth for identity; privacy by default; authorization belongs to
  Phase 4's scoped model, never to a profile column.
- **Consequence:** public team pages will use a separate projection (view) with chosen columns.

## D15. Avatars in a private bucket, uploaded through a Server Action

- **Decision:** bucket `avatars` is private; the server checks the bytes, picks the path
  (`{user_id}/{uuid}.ext`) and uploads with the student's session; pictures are shown through
  short-lived signed URLs.
- **Reason:** students' faces are personal data; the browser must not choose names or paths.
- **Consequence:** showing avatars to others later needs a deliberate rule (a public projection or
  a second bucket), not a flag flip.

## D16. MFA enforced by the database once enrolled

- **Decision:** TOTP is optional; a user who enrolled it gets nothing from their rows at aal1
  (restrictive policies through `private.mfa_requirement_met()`), and the app routes them to the
  second step.
- **Reason:** UI checks can be skipped; the database cannot. This is also the foundation Phase 4
  needs to require aal2 for governance actions.
- **Consequence:** the first grant of the `private` schema to `authenticated` (usage + this one
  helper); the foundation test now checks an explicit allowlist.

## D17. `/manage` unavailable in production until Phase 4 (superseded by D19)

- **Decision:** production shows "L'espace des bureaux ouvre bientôt" on every `/manage` page for
  everyone; `next dev` keeps the Phase 1 shell as a preview with a fictional officer.
- **Reason:** authenticated is not authorized; no real permission model exists yet.
- **Consequence:** Phase 4 replaces `lib/manage-preview.ts` with scoped permissions checked by the
  database.

## D18. Fictional test accounts with a password, development only

- **Decision:** accounts `@comptes.example.test`, created by SQL script on non-production
  projects, sign in with a password through a dashed form that exists only when
  `AUTH_TEST_ACCOUNTS=on`.
- **Reason:** the client needs to try the site as each kind of user; fictional addresses cannot
  receive the sign-in code, and the hosted mailer only delivers to the project team.
- **Rejected:** a passwordless "sign in as…" switch (a bypass, too easy to leave on); real
  mailboxes (real people's data in development).
- **Consequence:** production never sets `AUTH_TEST_ACCOUNTS` (production checklist). The form adds
  no capability Supabase lacked (password sign-in is part of its API), only a page for it.

## D19. Authorization is computed by the database at request time

- **Decision:** a right is the conjunction of an open membership, a current mandate (or a backed
  delegation) on a position carrying the key, and an organization status that allows it, evaluated
  by `private.user_has_organization_permission` on every request. No role in the JWT, no cached
  permission set, no scheduled expiry. Replaces the Phase 1 `/manage` preview (D17).
- **Reason:** expiry and revocation must work without jobs or sign-outs (brief §25, §80); one
  function shared by RLS and the RPCs cannot drift.
- **Rejected:** custom JWT claims (stale until refresh), a nightly expiry job (authorization would
  depend on it running), checks in Next.js only (bypassable).
- **Consequence:** every policy and function calls the same helpers; a revoked right disappears on
  the next request.

## D20. Writes only through `security definer` functions

- **Decision:** `authenticated` has no INSERT/UPDATE/DELETE on governance tables; each action is a
  function that checks authority, MFA, ceiling, dates and states, writes in one transaction and
  audits.
- **Reason:** multi-row invariants (a succession ends and starts mandates at the same instant, an
  invitation creates a membership and a mandate) cannot be expressed safely as row policies, and
  every action must be audited atomically.
- **Consequence:** the advisor's "authenticated can execute SECURITY DEFINER" warnings are expected
  (D21); new mutations follow the same pattern.

## D21. Accepting the advisor's SECURITY DEFINER warnings

- **Decision:** keep the governance RPCs executable by `authenticated`.
- **Reason:** they are the API. Each identifies the caller with `auth.uid()` and checks rights
  itself; `search_path` is pinned; pgTAP calls each as unauthorized users.
- **Consequence:** reviewing an advisor report means checking that every listed function is in
  [rls-policies.md](rls-policies.md#the-rpc-surface), not silencing the list.

## D22. Several permissive SELECT policies per table

- **Decision:** one policy per reading rule (own, team, platform) rather than one combined policy.
- **Reason:** each rule reviewable on its own line; volumes are small.
- **Consequence:** the advisor's "multiple permissive policies" warning is accepted; revisit if a
  table grows past tens of thousands of rows.

## D23. "Garant·e de continuité" instead of "School Responsible"

- **Decision:** the brief's School Responsible is a platform role named Garant·e de continuité,
  provisioned only by the project owner in SQL, with recovery powers only.
- **Reason:** the site is not validated by the school; the name must not suggest an official
  school position. Recovery must not depend on the people it replaces.
- **Consequence:** the BDE (or whoever it designates) chooses the person; the school can hold the
  role only if it agrees to, without the site claiming any official status.

## D24. Stay on Supabase

- **Decision (2026-10-19):** keep Supabase rather than rebuilding authentication, database
  hosting and storage ourselves.
- **Reason:** the limits met so far are free-plan limits (e-mail templates need custom SMTP, no
  automatic backups), not architectural ones; rebuilding auth, MFA, sessions and storage security
  would add risk with no gain; the schema is plain Postgres (migrations, RLS, functions) and stays
  portable.
- **Consequence:** production goes on the Pro plan for backups; the BDE configures its own SMTP
  (Brevo or similar) before launch.

## D25. Invitations and governance requests are in-app only (Phase 4)

- **Decision:** invitations, proposed presidencies and approvals wait in Mon espace › Invitations;
  no e-mail is sent.
- **Reason:** the generalized notification engine is a later phase, and Supabase's built-in mailer
  only sends sign-in codes; security never depends on an e-mail arriving.
- **Consequence:** the inviter is told to warn the person; the notification phase adds e-mails on
  top of the same rows.

## D26. Draft and published versions in the same tables (Phase 5)

- **Decision:** `association_profiles`, `association_gallery_items` and `association_team_entries`
  hold a `draft` and a `published` stage; publishing copies one into the other in a transaction.
- **Reason:** one schema, one set of constraints for both; the preview and the public page use the
  same payload builder; no JSON snapshot that could drift from the columns.
- **Consequence:** public reads go only through functions that pick the published stage
  (`public_association*`); the page team reads the draft through RLS and `association_editor`.

## D27. Field-level merge instead of locking (Phase 5)

- **Decision:** a save sends the changed fields and the values the editor loaded; the database
  refuses only a field someone else changed meanwhile (`draft_conflict`). Publishing names the
  revision that was previewed (`draft_changed` otherwise).
- **Reason:** small teams edit at odd hours from phones; locks get stuck and last-write-wins loses
  work silently.
- **Consequence:** the editor saves per section; a conflict asks to reload, keeping what was typed.

## D28. Images only through the site's own routes, re-encoded on upload (Phase 5)

- **Decision:** the `association-media` bucket is private; images are served by
  `/media/associations/…` (public only while a public page uses them, checked by a Storage policy
  as the visitor) and `/media/apercu/…` (page team, never cached). Every upload is re-encoded to
  WebP without metadata by `sharp` on the server.
- **Reason:** a draft image must never leak through a guessable or cached URL; photos carry GPS
  and device metadata; a re-encode neutralises malformed files.
- **Consequence:** `next/image` optimizes public images with a 5-minute cache (`minimumCacheTTL`),
  preview images are `unoptimized`; uploads use a route handler (progress) with an origin check.

## D29. Each member owns their public presentation (Phase 5)

- **Decision:** whether someone appears on the public team, with their photo and a line, is their
  own setting (`membership_public_profiles`); photo off by default; editors may hide, never expose.
- **Reason:** the site publishes students' names; consent has to come from the person, and a
  position title is enough to show a bureau exists.
- **Consequence:** member photos never appear in previews; the portrait route re-checks consent on
  every request.

## D30. Former addresses redirect forever and are never reused (Phase 5)

- **Decision:** a changed slug goes into `organization_slug_history`; it redirects permanently and
  no other organization can take it.
- **Reason:** shared links (posters, Instagram bios) keep working, and nobody can impersonate an
  association by grabbing its old address.

## D31. BDE moderation is withhold/release only (Phase 5)

- **Decision:** `platform.content.moderate` can take a page off the site with a reason and put it
  back; it cannot read drafts or change content.
- **Reason:** the brief's oversight without routine access to associations' private work.
- **Consequence:** the association sees the reason in its editor and fixes its own page.

## D32. The site address is configured, never guessed (Phase 5)

- **Decision:** absolute URLs (Open Graph, canonical, sitemap) use the server setting `SITE_URL`;
  empty in production until the BDE buys its domain, and the sitemap is then empty.
- **Reason:** the domain is the client's decision; a guessed one would leak into shared previews.

## D33. A post is an identity plus revisions frozen at submission (Phase 6)

- **Decision:** `posts` holds the identity and the state (address, publication, schedule,
  moderation); `post_revisions` holds numbered content snapshots. Only a draft changes; from
  submission on, a trigger freezes the revision for every role. Editing frozen content opens a new
  revision; publishing moves `published_revision_id`.
- **Reason:** the live article must not change while someone edits it, an approval must apply to
  exactly what was read, and history and restoring come with the model.
- **Rejected:** Phase 5's draft and published stages (D26), which keep no history and give an
  approval nothing fixed to bind to; one JSON snapshot column on `posts` (uncontrolled, hard to
  validate and to search).
- **Consequence:** every edit of a live post is reviewed and published again; storage grows with
  each version (whole snapshots, no diffs).

## D34. An approval belongs to one frozen revision (Phase 6)

- **Decision:** approving sets the status of that revision and records a `post_reviews` row with
  the md5 hash of its content; publishing checks the status of the exact revision named. A new
  revision never inherits an approval, and changing the policy neither grants nor revokes one.
- **Reason:** the brief's "approval cannot be reused for altered content"; the freeze enforces it,
  the hash lets anyone verify it afterwards.
- **Rejected:** approving the post (any later edit would ride on it); checking a hash only at
  publication (it would protect nothing if the content could still change).
- **Consequence:** in approval mode, fixing a typo in a live article needs a new approval.

## D35. The editorial policy belongs to each association, direct by default (Phase 6)

- **Decision:** `organization_editorial_settings.review_mode` is `direct` (publishers publish
  alone) or `approval` (a second person with `posts.approve` approves, never their own writing),
  chosen with `posts.settings` and the second factor. New organizations start in `direct`.
- **Reason:** many associations start with one or two people holding content keys; approval with
  self-review refused would leave them unable to publish. Teams that want a second reading turn it
  on.
- **Consequence:** the BDE cannot impose approval on an association; its oversight is moderation
  (D39). Direct publications still leave an approval record (`published_directly`).

## D36. The article body is a validated JSON document, never HTML (Phase 6)

- **Decision:** a small subset of the Tiptap / ProseMirror document (paragraphs, two heading
  levels, lists, quotes, rules, line breaks, library images; bold, italic, links), checked by a
  column constraint, normalized by the server and rendered element by element (`RichText`).
- **Reason:** no HTML sanitizer to trust and keep up to date, nothing ever printed as markup;
  revisions stay comparable; the renderer can change without migrating content; images as library
  references keep the media rules (privacy, removal) enforceable.
- **Rejected:** sanitized HTML (bypasses, `dangerouslySetInnerHTML`); Markdown (raw HTML
  passthrough and link edge cases, hard to validate in SQL).
- **Consequence:** a new kind of content (an embed, a table) needs the constraint, the normalizer
  and the renderer changed together, in a migration and a release.

## D37. Scheduled publishing runs in the database, authorized by the approval (Phase 6)

- **Decision:** a schedule names one approved revision and one instant; a pg_cron job calls
  `private.run_scheduled_publications()` every minute, which claims due posts with `skip locked`,
  re-checks moderation, the association, its page and the images, and publishes or records a
  failure code. The scheduler's own rights are not re-checked at execution. No automatic retry.
- **Reason:** nothing in the browser or the app server has to be awake; each post is one
  transaction and a second run finds nothing to do; an approved announcement must not vanish
  because a mandate ended in between, while cancellation, moderation, suspension or an offline
  page still stop it.
- **Rejected:** an app cron calling an endpoint with the secret key (a privileged HTTP surface and
  a second scheduler); an Edge Function through `pg_net` (more parts, same result); retries (a
  refused publication needs a person's decision).
- **Consequence:** every environment needs `pg_cron` (the migration creates the job where the
  extension exists); failures show on the desk with their reason and in the audit log.

## D38. Feed order is the first publication, with keyset pagination (Phase 6)

- **Decision:** `first_published_at` is set once; republishing, unarchiving or editing never moves
  a post. Pages are cut on `(first_published_at, id)`.
- **Reason:** a corrected typo must not push an old article to the top, and new posts must not
  shift or repeat what a reader is scrolling through.
- **Consequence:** bringing something back to attention is the BDE's prominence (D40), not a
  republication.

## D39. Moderation hides posts; reports stay anonymous (Phase 6)

- **Decision:** like pages (D31), the BDE hides a post with a reason and the second factor and can
  restore it; it reads only what was public, never drafts. A hide overrides publication: nothing
  the association does shows the post again. Reports keep the reporter for abuse handling only;
  their audit line has no actor and no organization.
- **Reason:** the brief's oversight without routine access to associations' work; students must
  be able to report without the association learning who did.
- **Consequence:** the association sees the hide and its reason, never the reports. Moderators
  cannot see the images of a hidden post (they stop being public).

## D40. Site-wide prominence is the BDE's, pins are the association's (Phase 6)

- **Decision:** `platform.content.feature` (BDE offices, not grantable) sets up to three
  `featured` posts from any association and up to two `important` ones, BDE posts only, with an
  optional end within 60 days. `posts.publish` pins up to three posts on its own association
  page.
- **Reason:** the campus front is the BDE's editorial space, an association's page is its own;
  only the BDE may look like an official notice.
- **Consequence:** expiry is read at query time (no job); hiding, unpublishing and archiving
  reset both, and the limits count only posts on display (fixed forward on 2026-10-23, see D43).

## D41. Post images live in the association's library (Phase 6)

- **Decision:** no new bucket: posts reference `association_media` by id (cover and inline), each
  revision's images are recorded in `post_revision_media`, authors with `posts.create` may upload,
  and an image any revision uses is never removed.
- **Reason:** one place for re-encoding, alt text, quotas and the public/private rule (D28); old
  versions must stay restorable and the live one must never lose an image.
- **Consequence:** an image becomes public only while a public post's live revision (or a public
  page) uses it; an image that any version of a post uses can never be removed, so the library
  (quota 300) keeps every image of every post's history (deleting a never-published draft frees
  its images).

## D42. Publishing notifications are in-app states and audit events (Phase 6)

- **Decision:** no e-mail or push: the desk and the editor show reviews, notes, failed schedules
  and hides; every step is an audit action.
- **Reason:** as D25, the notification engine is Phase 10, and no publishing rule depends on a
  message arriving.
- **Consequence:** Phase 10 subscribes to the audit actions listed in
  [publishing.md](publishing.md#notifications) (`post_submitted`, `post_approved`,
  `post_changes_requested`, `post_schedule_failed`, `post_hidden`…).

## D43. Leaving the site settles what was planned for a post (Phase 6, fix forward)

- **Decision:** `unpublish_post` and `archive_post` also cancel a pending or failed schedule and
  reset the BDE's prominence; the featured/important limits count only posts the site shows;
  `set_post_pin` refuses a hidden post; a bad prominence end date has its own refusal
  (`prominence_period`). Migrations `20261023084644_release_post_prominence` and
  `20261023085021_settle_post_schedule_and_pins`.
- **Reason:** found while building the screens: a scheduled update brought an unpublished or
  archived post back online, and a featured post that left the site kept a slot nobody could
  see or free.
- **Consequence:** taking a post off the site is final until someone publishes it again; the
  audit line of the unpublication or archiving records whether a schedule or a prominence went
  with it.

## D44. Events are their own model, owned by one organization (Phase 7)

- **Decision:** `events` is a table of its own (not a kind of post), owned by one organization for
  ever (`event_owner_locked`), with three concerns kept apart: publication
  (draft/published/unpublished), status (scheduled/cancelled, irreversible) and BDE moderation
  (hidden). "Past" is computed from `ends_at`, never stored.
- **Reason:** dates, places, capacity and registrations have rules a post does not; a cancelled
  event must stay readable with its reason, and a hidden one must keep its registrations.
- **Consequence:** an event with registrations is cancelled, never unpublished or deleted; only a
  draft that was never online can be deleted. Co-organizers are a credit, not a right.

## D45. Seats are counted under the event's lock, by the database only (Phase 7)

- **Decision:** `register_for_event` locks the event row and maintains `confirmed_count` and
  `waitlist_count`; `CHECK (capacity is null or confirmed_count <= capacity)` and a unique partial
  index (one active registration per student and event) make overbooking and double registration
  impossible. A null capacity means unlimited. Registering twice returns the same registration.
- **Reason:** the brief's 20-students-for-one-seat case; counting rows from the app would race.
- **Consequence:** the counters are written only by the functions (lock order: event, then
  registrations); the concurrency suite runs on every push.

## D46. The waiting list is first come, first served, and only while registration is open (Phase 7)

- **Decision:** waiting places are ordered by a sequence; a freed seat goes automatically to the
  first in line, who is told, as long as registration is open. After the closing time nobody is
  promoted.
- **Reason:** fairness without a person deciding; a late promotion would surprise someone hours
  before the start.
- **Consequence:** organizers who want to fill a late seat raise the capacity knowingly (which
  promotes in order). Leaving the list is always possible before the start.

## D47. "À l'affiche" is the BDE's, pins are the association's (Phase 7)

- **Decision:** as for posts (D40), `platform.content.feature` puts up to three events "à
  l'affiche" of the agenda and the home page, for 60 days at most; `events.publish` pins up to
  three events at the top of its own association's page.
- **Reason:** no association can take over the home page through its own metadata.
- **Consequence:** prominence is released when an event is cancelled, hidden or taken offline.

## D48. Participants are personal data with their own keys (Phase 7)

- **Decision:** `events.attendees.view`, `.manage` and `.export` are sensitive, grantable,
  never delegable; the list shows names, statuses, references and dates only (no e-mail); every
  export is audited; a student's registrations are not audit lines.
- **Reason:** organizing an event needs names, nothing more; `audit.view` must not become a way to
  read who registered; the BDE must not get routine access to associations' participants.
- **Consequence:** the BDE reads public information and counts only; the "Événements" template
  sees and manages participants but does not export.

## D49. Messages go through an outbox; e-mail is a separate worker (Phase 7)

- **Decision:** every message is a `notification_outbox` row written in the same transaction as
  the change it reports, deduplicated by key, read in the student's Notifications; a worker
  (`/api/notifications/send`, the only user of the privileged client) e-mails pending rows with a
  lease, retries and backoff. Reminders are queued by the pg_cron job `enqueue-event-reminders`.
- **Reason:** a message must never be lost or doubled by a failed delivery, and a delivery problem
  must never touch a registration. The sender's address and provider are the BDE's choice.
- **Consequence:** without a transport configured (the case today) students get messages in the
  site only and the desk shows e-mails waiting. The full notification centre stays Phase 10.

## D50. Event reads fixed forward (Phase 7)

- **Decision:** `20261025090000_event_read_fixes`: the BDE list's archive takes the 100 most
  recent past events (it took the oldest); the article editor gets the linked event's address;
  the participant counts list each person once (a cancelled row of someone who registered again
  is not a cancellation).
- **Reason:** found while building the screens and checking them on the development project.
- **Consequence:** same signatures and grants; covered by new checks in `events.test.sql`.

## D51. A campaign's state is derived; three stored concerns (Phase 8)

- **Decision:** a campaign stores its publication (draft/published/unpublished), its status
  (scheduled/paused/closed/cancelled, cancelled irreversible) and BDE moderation (hidden) apart;
  what visitors read (open, upcoming, paused, closed, cancelled) is computed by
  `private.campaign_state` from them and the clock. Positions close with the campaign or earlier.
- **Reason:** no job to flip campaigns open or closed (one that fails would leave a deadline open);
  the deadline is decided by the database at the moment it receives a submission.
- **Consequence:** a campaign that received submissions is paused, closed or cancelled, never taken
  off the site or deleted; a cancelled one stays readable with its reason.

## D52. The form is one versioned JSON document, not normalized tables (Phase 8)

- **Decision:** each form version is a single validated document (sections, questions with stable
  ids, options with stable ids) in `recruitment_form_versions.schema`, instead of the brief's
  suggested question/option tables. One draft and one published version at a time; a published
  version is frozen by trigger and superseded, never rewritten; submitted applications point to
  their version.
- **Reason:** a version must be immutable as a whole (answers read against the questions as they
  were); one document is validated, frozen, duplicated and compared in one place, and a builder edits
  it without dozens of row-level writes. Whitelisted keys per type keep it data, never code.
- **Consequence:** answers are a JSON object keyed by question id, checked by
  `application_answer_errors` (and mirrored in TypeScript for early messages). Phase 9 reads
  answers through the same schema.

## D53. A candidate's steps are not governance audit lines (Phase 8)

- **Decision:** starting, saving, uploading, submitting and withdrawing are recorded in
  `application_events`, read by the candidate only; the governance audit records the team's and the
  BDE's actions on campaigns, positions, forms and settings, and the purge in counts.
- **Reason:** `audit.view` is held by association officers; it must never reveal who applied, or
  that someone withdrew.
- **Consequence:** the desk shows counts; who applied becomes visible only to Phase 9 reviewers, with
  their own audit.

## D54. Nobody but the candidate reads an application in Phase 8 (Phase 8)

- **Decision:** applications, their answers, history and documents are readable by their candidate
  only (RLS and Storage policies); team reads (`recruitment_dashboard`, `recruitment_editor`) and
  the BDE list return counts; `recruitment.applications.*` stay inactive.
- **Reason:** the brief forbids giving the president, the BDE or the guardian bulk access before the
  review system exists, and Phase 9 designs reviewer access per campaign and position.
- **Consequence:** campaigns can run end to end, but no one can read submissions until Phase 9: the
  BDE must not open real campaigns before then (report, manual steps).

## D55. Documents are reserved, uploaded with the candidate's session, then confirmed (Phase 8)

- **Decision:** a private bucket; the upload route checks the real content (magic bytes, no macros
  or embedded objects), the database reserves an anonymous path for the caller's own draft, the file
  is stored with the candidate's session (the Storage policy allows only that reserved path), and a
  confirmation makes it count. Downloads stream through an authorized route as attachments; no
  signed URL is handed out. Deleted files are queued and removed by a service-role worker.
- **Reason:** no privileged client in the user's path; a path no one reserved can never be written;
  a file never served inline cannot run in the site's origin.
- **Consequence:** no malware scanner exists (disclosed); the BDE decides one before Phase 9
  reviewers open files.

## D56. Eligibility is the self-declared study year (Phase 8)

- **Decision:** a campaign (or a position) may restrict applications to study years, compared with
  the year the student declared in their profile; anything else is a free note on the fiche.
- **Reason:** the site is not validated by the school: there is no directory to check a programme,
  a campus or a year, and the profile's programme is free text.
- **Consequence:** the fiche says the rule depends on the profile; a student without a declared
  year cannot apply to a restricted position.

## D57. Articles point to a campaign, shown live (Phase 8)

- **Decision:** as for events (D44's link, Phase 7), an article stores only a campaign id
  (`posts.recruitment_campaign_id`); its page shows the campaign's state, deadline and positions
  live, and nothing when the campaign is not public.
- **Reason:** "Finance recrute !" articles must never advertise a closed or hidden campaign as open.
- **Consequence:** changing the link on an article that is online needs `posts.publish`.

## D58. Recruitment fixed forward (Phase 8)

- **Decision:** `20261026090400_recruitment_fixes`: `private.form_invalid` (which only raises) is
  `volatile` (declared immutable, plpgsql_check saw it evaluated with constant arguments); an image
  uploaded by a recruitment manager is audited under `recruitment.campaigns.manage`.
- **Reason:** found by the CI lint and while building the wizard's cover upload.
- **Consequence:** same signatures and grants.

## D59. An association's leadership reads its own applications, never another's (Phase 9)

- **Decision:** the recruitment review keys are organization keys: offices carry them all, the
  vice-presidency every one but the export, the recruitment manager all, the reviewer template
  reading, files and reviews. They open the campaigns of the holder's own organization only; the
  BDE offices' keys open the BDE's own campaigns. The continuity guardian has none.
- **Reason:** the project owner's rule (each association's president, vice-president and team can
  view their association's applications and cannot view another association's); the brief forbids
  routine BDE access to associations' applicants.
- **Alternatives:** committee-only access (the leadership would have to appoint itself to every
  campaign); a BDE-wide reader (refused by the brief).
- **Consequence:** a president can open every application of their association's campaigns from
  day one; anyone else needs a position carrying the keys or a committee seat.

## D60. The key route stops at the campaign's seal (Phase 9)

- **Decision:** twelve months after a campaign closes (or when it is archived), the organization
  keys open it only for people who already held them at that moment; anyone else needs a
  committee appointment with a written purpose.
- **Reason:** next year's officers must not inherit last year's candidates (cross-year
  restriction of the brief), while a contested result can still be looked at, on purpose.
- **Consequence:** `private.campaign_sealed_at` and `private.recruitment_key_route`; the committee
  page says when a campaign is sealed.

## D61. Committees: one campaign, chosen powers, a scope and an end date (Phase 9)

- **Decision:** `recruitment_committee_members` rows (an active member, `view` plus chosen powers,
  scope campaign / positions / assigned, at most 18 months), never above the appointer's own
  powers, checked live at every request (membership, dates, revocation).
- **Reason:** the brief's scoped reviewer access without creating positions for one season, and
  least privilege (a reviewer who only sees what is confided to them).
- **Consequence:** `private.application_can` combines both routes; `my_access` exposes a committee
  seat so the navigation opens without a key.

## D62. Scores support decisions; nothing decides by score (Phase 9)

- **Decision:** versioned grids, a plain weighted total with its basis, blind reviews (others'
  reviews need `view_team`), a required number of reviews that can only be bypassed with a written
  reason; no ranking, sort or threshold by score anywhere, no AI.
- **Reason:** the brief's "no AI screening and no automatic decisions"; transparency for the
  people deciding and, through access requests, for the candidate.
- **Consequence:** the list sorts by date or name only; the average is shown, never acted upon.

## D63. The candidate sees a projection, released deliberately (Phase 9)

- **Decision:** `private.candidate_status` derives what the candidate is told; the internal
  pipeline, proposals and validated decisions stay internal until someone with `release`
  announces them; message templates take five allowlisted placeholders replaced as text.
- **Reason:** a candidate must never learn an outcome by accident (a proposal, a shortlist, a
  premature e-mail), and templates must not become a way to leak internal data or inject markup.
- **Consequence:** release is its own step (now or scheduled); messages are queued in the release
  transaction.

## D64. Approval policies and places are checked under the position's lock (Phase 9)

- **Decision:** single / two different approvers / one plus the presidency; finalizing an offer
  counts the position's pending and accepted offers under `pg_advisory_xact_lock` and needs a
  written reason beyond the places; one pending decision and one released outcome per application
  (unique partial indexes).
- **Reason:** two approvers acting at once must not fill one place twice (tested in parallel
  sessions).
- **Consequence:** overrides are recorded on the decision and in the history.

## D65. Interview slots are exclusive; booking is atomic (Phase 9)

- **Decision:** one booking per slot (unique index), an interviewer never in two overlapping slots,
  the candidate books and may change until 24 hours before; the link is given only once booked.
- **Reason:** the brief's slot booking without double booking, and no meeting link floating
  around before it is someone's.
- **Consequence:** a repeated booking of the same slot changes nothing; a slot taken first by
  someone else is refused with "slot_unavailable".

## D66. Reviewers download with their own session (Phase 9)

- **Decision:** `public.recruitment_document` checks the `documents` power and records the
  opening; the Storage read policy honours that record for two minutes, for that person and that
  file, checking the power again. The route reads with the caller's session.
- **Reason:** every opening must be recorded and the privileged key stays out of the user's path
  (security-foundations: a permission problem is fixed with a policy, not that client). A first
  version used the privileged client; it was replaced before release (D70).
- **Alternatives:** signed URLs (shareable, refused in Phase 8); a reviewer Storage policy without
  the record (openings would escape the log).
- **Consequence:** a reviewer can read nothing in Storage they did not open through the function
  in the last two minutes.

## D67. Onboarding is an invitation, never a right (Phase 9)

- **Decision:** after an accepted offer, `start_recruitment_onboarding` calls the Phase 4
  `invite_member` (optionally an ordinary position and a mandate end); the person accepts it like
  any invitation. Offices are never given this way.
- **Reason:** accepting an offer must not grant permissions by itself; the team's leadership
  stays in control of who gets which keys.
- **Consequence:** the offer shows the invitation's status; the decision is not linked to a
  position assignment.

## D68. Data rights go to a privacy officer, not to the BDE (Phase 9)

- **Decision:** a platform role `privacy_officer` with `platform.privacy.requests`, provisioned by
  the project owner only; reports and erasures need a written reason and the second factor and are
  audited about the person concerned.
- **Reason:** answering access and erasure requests requires seeing everything held about a
  candidate, which no association officer, BDE office or guardian should have routinely.
- **Consequence:** until the operator designates someone, requests cannot be handled in the app
  (manual step).

## D69. No malware scanner yet; attachments only (Phase 9)

- **Decision:** files are never displayed inline (attachment, `nosniff`, sandboxed CSP), content
  is checked at upload (Phase 8), and no antivirus runs.
- **Reason:** the owner did not choose a scanning service; sending CVs to an outside scanner is a
  data-protection decision of its own.
- **Consequence:** disclosed in the report and the docs; to decide before real campaigns.

## D70. Phase 9 fixed forward (Phase 9)

- **Decision:** `20261026161915_recruitment_review_followups`: `public_recruitment_privacy` also
  returns the retention of selected applications, and `recruitment_campaign_access` the
  campaign's organization (a campaign opened under another association's address is redirected).
  `20261026163800_recruitment_reviewer_file_reads`: D66's Storage rule.
- **Reason:** found while building the screens and verifying them on the development project.
- **Consequence:** same signatures and grants.

## D71. A success whose form disappears is announced (Phase 9)

- **Decision:** when an action succeeds and the refreshed page no longer contains its form (a
  question answered, a slot booked, a review submitted), its message is shown by a status line
  pinned to the bottom of the screen (`DoneAnnouncer`, read out by screen readers).
- **Reason:** without it the confirmation vanished with the form.
- **Consequence:** forms that stay keep their inline message; nothing is announced twice.

## D72. One notification model, three layers (Phase 10)

- **Decision:** a catalog (`notification_topics`, `notification_types`), the in-app record
  (`notifications`, the Phase 7 outbox renamed with its rows and keys kept) and one delivery row
  per channel (`notification_deliveries`). Every producer calls `private.notify`.
- **Reason:** the outbox mixed two channels in one status; preferences, suppression, retries and
  provider events need their own rows. Keeping `dedupe_key` means a producer firing again after the
  migration still collides with its old row.
- **Alternatives:** a new table beside the outbox (two systems); a queue extension (pgmq) — more
  moving parts for the volume of a BDE.
- **Consequence:** no producer inserts rows itself; the site reads only through the centre's
  functions.

## D73. E-mail is sent by a Supabase Edge Function, woken by the database (Phase 10)

- **Decision:** `notifications-worker` (Deno), called every minute by pg_cron through pg_net with
  a bearer token kept in Vault, connected to the database with `SUPABASE_DB_URL`; it calls only
  private functions. The Next.js worker route and its privileged client are removed.
- **Reason:** nothing scheduled the Phase 7 route, it needed the secret API key in the site, and
  the site's host is not decided. The database already owns the queue and the clock.
- **Alternatives:** a cron on the site's host; a third-party scheduler.
- **Consequence:** the Brevo key lives only in the function's secrets; the site never sends mail.
  `verify_jwt` is off for both functions: the token compared in the database is the gate.

## D74. Three delivery modes, off by default (Phase 10)

- **Decision:** `off` (nothing claimed), `capture` (rendered and stored, never sent) and `live`,
  set by the operator with `private.set_notification_config` (audited). Live needs a sender, the
  site's address and the key, or nothing is claimed.
- **Reason:** test the whole chain on the development project without sending anything, and never
  send from an environment by accident.
- **Consequence:** the development project runs in `capture`; production waits for the BDE's domain.

## D75. Retries, unknown outcomes and the provider's events (Phase 10)

- **Decision:** a 5-minute lease under `skip locked`; exponential backoff with jitter, at most 6
  attempts; a timeout after sending is `outcome_unknown`, retried only after 10 minutes; each
  message carries our key in `X-Mailin-custom`, and an attempt Brevo acknowledged (its `request`
  or `delivered` event) is reconciled instead of sent again.
- **Reason:** Brevo has no idempotency key; a blind retry after a timeout could send twice.
- **Consequence:** a duplicate is possible only when Brevo accepted a message and never sent its
  events for 10 minutes; a lost e-mail is not.

## D76. Essential, operational, optional (Phase 10)

- **Decision:** what concerns a step in progress or the account's security always arrives (and has
  no unsubscribe link); operational messages always stay in the centre, their e-mail can be turned
  off; BDE announcements and followed associations are opt-in by e-mail. Every change is recorded
  (`notification_preference_changes`), including from the one-click link.
- **Reason:** a student must not miss a registration, an offer or a security change; everything
  else is their choice (and the consent must be provable).
- **Consequence:** an audience's e-mail count is an estimate made from these choices.

## D77. Confidential e-mails say nothing (Phase 10)

- **Decision:** every message about an application is `confidential`: a neutral subject and body,
  no position, reference, message, outcome or "important" mark; an offer and a refusal read the
  same. The details are read on the site, signed in.
- **Reason:** e-mail is read on shared screens and lock screens, and kept by providers.
- **Consequence:** candidates open the site to read their news (a link takes them there).

## D78. Messages to an audience, not a chat (Phase 10)

- **Decision:** broadcasts are prepared, estimated, then submitted; the database resolves and
  freezes the audience (never a list of addresses from a browser), limits them (3/day BDE, 5/day
  per association, 5 000 people for members or followers), requires the second factor for e-mail
  and a second BDE officer's approval for a campus-wide e-mail, re-checks each person when
  dispatching and audits each step. `communications.send` is grantable, not delegable.
- **Reason:** the brief's campus-wide channel without spam, mistakes or a single person able to
  e-mail every student.
- **Consequence:** no replies or threads; associations keep their own channels for discussion.

- **Consequence:** same signature and grants; a pgTAP test covers the shape.
